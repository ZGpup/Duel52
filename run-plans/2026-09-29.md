# Run plan — 2026-09-29

Eight jobs, and each gets its own machine: seven on 32-core CPU nodes (two of them builds) and
three on 40 GB GPUs (one of them a build). Every job is **resumable by resubmitting the same
file**, so a time limit or a preemption costs at most the work in flight.

## 1. One-time setup (login node)

Put both checkouts on scratch storage rather than in home, because the base run's buffer and
shards run to tens of GB. The mod-traps run lived under `/gscratch/stf/asagil/duel52/`.

```bash
cd /gscratch/<group>/<you>/duel52          # or wherever

git clone https://github.com/ZGpup/Duel52.git Duel52              # main: CPU jobs
git clone -b rnad https://github.com/ZGpup/Duel52.git Duel52-rnad  # rnad: GPU jobs

# Rust, once per account (skip if `cargo --version` already works)
curl --proto '=https' --tlsv1.2 -sSf https://sh.rustup.rs | sh -s -- -y
. "$HOME/.cargo/env"
```

Python must be **3.11 or newer** (the trainer needs `tomllib`). `module load` one if the system
Python is older. Then build one venv per checkout. They differ only in which PyTorch they get:

```bash
cd Duel52
python3 -m venv .venv
.venv/bin/pip install -U pip maturin numpy pytest
.venv/bin/pip install torch --index-url https://download.pytorch.org/whl/cpu   # CPU-only: ~200 MB not 2.5 GB
cargo fetch                    # downloads the bindings' crates so the build job needs no internet

cd ../Duel52-rnad
python3 -m venv .venv
.venv/bin/pip install -U pip maturin numpy pytest
.venv/bin/pip install torch    # the default wheel is the CUDA build, which is what the GPU jobs need
cargo fetch
```

Do not build on the login node. `00-build` builds on a compute node with
`-C target-cpu=native`, which is worth 20–40% of throughput. A native binary can crash with
"illegal instruction" on an older CPU, so each checkout is built on the kind of node that
runs it.

⚠️ **If the 32-core nodes are a mix of CPU generations**, build portable instead:
`sbatch --export=ALL,PORTABLE=1 ...00-build.sbatch`. That costs the 20–40% but cannot crash.

## 2. Submit

Every `.sbatch` hard-codes 1 node, the core count, memory and a time limit. The account and the
partitions are the cluster's, so `submit.sh` takes them as environment variables:

```bash
cd Duel52
MAIN=$PWD RNAD=$PWD/../Duel52-rnad \
ACCOUNT=<account> CPU_PARTITION=<32-core partition> GPU_PARTITION=<gpu partition> \
    bash run-plans/2026-09-29/slurm/submit.sh
```

It queues both builds, and then every run job with `--dependency=afterok:<its build>`, so a
failing test suite holds everything behind it instead of letting eight jobs run on a bad build.

⚠️ **The GPU jobs ask for `--gres=gpu:1`.** If the cluster names its cards, e.g.
`--gres=gpu:a100:1`, edit the `#SBATCH --gres` line in `30-` and `31-` (and in `submit.sh` for
the GPU build) to get a 40 GB card.

**To submit one job by hand** (e.g. after a failure), `cd` to the right checkout first, because
jobs run in the directory they were submitted from:

```bash
cd Duel52      && mkdir -p slurm-logs && sbatch -A <acct> -p <part> run-plans/2026-09-29/slurm/13-analysis-best-traps.sbatch
cd Duel52-rnad && mkdir -p slurm-logs && sbatch -A <acct> -p <part> run-plans/2026-09-29/slurm/30-rnad-canonical.sbatch
```

⚠️ **`slurm-logs/` must exist before `sbatch`**, or slurm drops the job's output without a
word. `submit.sh` creates it.

## 3. What to watch

`squeue -u $USER`, and `tail -f slurm-logs/<job>-<id>.out` in the relevant checkout. Every log
opens with a banner naming the node, the CPU, whether it has AVX-512, the git commit and the GPU.

- **Analysis (10–14):** one line per chunk, `── chunk k/n: 1,024 games from seed …`, then
  nothing for **~2–5 hours**, because all 1,024 games of a chunk are in flight at once and
  finish together. A silent log is normal. `ls analysis/<dataset>/<agent>/` shows the finished
  chunks, and each one has a `meta.json` with its `games_per_sec`. **Read the first chunk's
  figure** to check the estimate.
- **Base training (20):** a block per generation, ~25 minutes apart. Watch the gate score
  settle toward 0.50 (the threshold is 0.50, so it promotes nearly every time) and the
  `random`/`greedy` panel rows climb to 1.000. Five refusals is not a crash. Eight in a row ends
  the run by design.
- **R-NaD (30, 31):** the `bench` block first, then a line every 10 steps, and an eval block
  (`netsample` vs `random` and `greedy`) every 1,500 steps. ⚠️ **Read the bench's projection.**
  Between ~20,000 and ~50,000 steps in 24 h, leave everything alone. Outside that range,
  `scancel` the job, copy the `entropy_schedule_size` and `target_network_avg` the bench's last
  line suggests into the config, delete the run directory, and resubmit.

## 4. Resubmitting

| Job | After a time-limit kill or preemption |
|---|---|
| 10–14 | Resubmit the same file. Chunks with a `meta.json` are skipped, and the one that was killed replays from its start |
| 20 | Resubmit with the hours that remain (next paragraph). The script adds `--resume` by itself, and the run continues **inside** the interrupted generation |
| 30, 31 | Resubmit the same file. R-NaD's `hours` counts across resumes, and `--resume` is automatic once `state.pt` exists |

⚠️ **Job 20 only: `hours` restarts at every invocation.** A plain resubmit would buy another
full 24 h. Pass what is left:

```bash
python3 -c "import json; print(24 - sum(json.loads(l)['seconds'] for l in open('runs/base-32c/log.jsonl'))/3600)"
sbatch -A <acct> -p <part> --export=ALL,HOURS=<that> run-plans/2026-09-29/slurm/20-train-base.sbatch
```

**To get more analysis games after a job finishes**, resubmit with a larger count, e.g.
`--export=ALL,GAMES=10240`. Only the new chunks are played, and they continue the same seed
sequence. Keep counts at multiples of 1,024.

## Why each job is what it is

### 1. The analysis corpora (jobs 10–14)

`duel52 analyze` plays each agent **against itself** and writes one corpus per agent. The
document then puts the corpora side by side. So "A vs B" here means two columns, not a match.
Items 1a and 1b both need `32c-24h-best` on canonical rules, and **job 10 serves both**:

- **`analysis/split-4096`** (1a and 1b, part 1): `32c-24h-best`, `lane-gen032`, and the traps
  agent **playing canonical rules** as a flagged control column. The first two show what +190
  Elo of strength changes about how the game is played. The third shows how much of the traps
  agent's style is the ruleset and how much is simply being a different net.
- **`analysis/two-blast-four-bomb-4096`** (1b, part 2): the traps agent on its own rules, and
  `32c-24h-best` **playing the traps rules** as the flagged control.

Rendered one after the other, the two documents give the 2 × 2 of {canonical-trained,
traps-trained} × {canonical rules, traps rules}.

**Throughput estimate** (no box measurement, as asked). The analysis corpora on disk, 8-core
laptop, eval batch 32:

| agent | @64 | @1000 |
|---|---:|---:|
| `lane-gen032` (128 × 3) | 2.83 g/s | 0.149 g/s |
| `32c-24h-best` (128 × 6) | 1.43 g/s | — |

- 64 → 1000 sims (15.6×) cost gen032 19×, so the cost per sim grows a little with budget.
  Taking 1000 → 4096 (4.1×) as ~4.7× puts gen032 at ~0.032 g/s on the laptop.
- The 128 × 6 trunk ran at 0.505× the 128 × 3 at equal sims.
- A 32-core node here is ~4× the laptop. That is `train-24h-32c.toml`'s K = 4, and the
  mod-traps run confirmed it on this cluster: 20.2 self-play games/sec measured against 20.4
  predicted.
- So: **gen032 ≈ 0.13 g/s (~11,000 a day), 128 × 6 ≈ 0.064 g/s (~5,500 a day)**. The traps
  rules ran ~7% slower in the 256-sim corpus, which is where 13 and 14 get their extra hours.

**Chunks of 1,024, not 250.** The eval batch is clamped to the games each thread owns, and
32 threads × 32 in flight = 1,024. A 250-game chunk would run 8 in flight per thread, which the
laptop measured at 0.6× the throughput of a full batch. The cost is that a chunk takes ~4.4 h
for a 128 × 6 net and a kill loses up to that, which is why the time limits are 48 h.

**Memory.** A search tree is ~400 KB per game at 256 sims, so ~6.4 MB at 4096, and 1,024 games
in flight is ~6.5 GB. The jobs ask for 32 GB.

**All five start at seed 1**, so every column plays the same deals up to its shortest length,
and a paired comparison is available where the document wants one.

### 2. Base rules, AlphaZero, from scratch (job 20)

**`configs/base.toml` was not moved into `configs/rules/`, and a registry entry was added
instead.** `configs/base.toml` is the `base` *variant preset* written out, and it sits beside
`split.toml` and `mirrored.toml` for the same reason. The registry already covers all three
presets (`rulesets.rs` enumerates `Variant::ALL`). Its defect for a training run is the label:
the preset carries `rules_name = canonical-2026-09`, so every shard and checkpoint would claim
the canonical name with a different hash. **`configs/rules/base.toml`** includes
`canonical.toml`, switches `variant = "base"`, and names itself `base-2026-09`. It hashes
identically to the preset (`8e5b455c61d08e5d`), which `rulesets.rs` now accepts as an alias,
and all 11 invariants pass.

**`configs/train-24h-32c-base.toml`** is the mod-traps config with three lines changed:

1. `rules_file = "configs/rules/base.toml"`.
2. **`encoding_slots = 34`, not 21.** Forced. The encoder asserts if one side of one lane
   holds more cards than it has slots. On the split deck that cannot exceed 21, but the shared
   deck's legality bound is 34. The limit is reached in practice, too: `gen063@1` against
   `random` put 20 cards on one side of one lane under the split deck, one short of its cap.
   An assert at hour 15 would also repeat on every `--resume`, because the run is seeded. The
   search cost is unchanged; only the fit's dense policy head widens (`action_dim` 2194 → 5509).
   **Every later command on these checkpoints needs `--encoding-slots 34`.**
3. Seed block 50,000,000.

Kept identical on purpose: the `128 × 6` trunk, 24,000 games a generation, and the LR tiers at
generations 21 and 39. Also kept, as decided: **the 0.50 gate**, and the `random` + `greedy`
panel, since every shipped checkpoint is split-deck and refused under these rules. So
`runs/eighth`, `runs/mod-traps-32c` and this run are one recipe on three games. The one
difference is `runs/eighth`'s 0.52 gate.

**No Stage 1 measurement** is needed. The mod-traps run was this recipe on this cluster, and
it did 63 generations in ~25.4 h. The one unknown is the base game's length: longer games
mean proportionally slower generations and nothing worse.

### 3. R-NaD, canonical and base (jobs 30, 31)

These run from the `rnad` branch, which now has `main` merged in (for `configs/rules/base.toml`
and these scripts) and two new configs:

- **`configs/rnad-24h.toml`** is `rnad-3h.toml` at 24 h, with the trunk deepened to
  **`128 × 6`** [ASSUMED]. That matches `32c-24h-best` and the base AlphaZero run, so the two
  learners can be compared at equal capacity. The regularisation schedule is re-sized to the
  estimated step count: **3,000-step iterations, `target_network_avg` 0.0033 (τ·size = 10)**,
  ~10–12 updates if a step takes ~2.5–3 s. `rnad-3h.toml` estimated ~1.5 s at `128 × 3` on an
  H100. A 40 GB A100-class card has about half the bandwidth, and the trunk is twice as deep.
  `bench` at the top of each job is the check (section 3).
- **`configs/rnad-24h-base.toml`** is the same on `configs/rules/base.toml` at
  `encoding_slots = 34`. Tensors ~2.5× wider give an estimated 15–20 GB peak, inside 40 GB.
  Its steps will be slower, so expect fewer of them.

Seeds 60,000,000+ and 80,000,000+ keep clear of every AlphaZero block.

⚠️ R-NaD on a GPU is **the same experiment on a resume, not the same bits.** GPU kernels are not
bit-deterministic. The games are still seeded.
